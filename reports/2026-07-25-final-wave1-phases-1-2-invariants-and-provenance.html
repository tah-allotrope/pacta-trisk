01 / Executive Summary

Executive Summary

What Was Delivered

Two phases of the six-phase Wave 1 "Consistency" plan landed and were verified this session. Phase 1 built tools/verify_refactor.R --invariants, a new acceptance mode that checks whether committed artifacts agree with each other — a question the existing byte-identity tool cannot ask, because it only compares a run against itself. Phase 2 used that detector to find and fix its first three real defects: a hardcoded data-source literal leaking into every engagement's client deliverable, a sector-prioritization function that silently ignored its own config, and an engagement config that could not reproduce its own documented run.

02 / Background & Objective

Background & Objective

PACTA + TRISK Vietnam is a synthetic-data platform demonstrating how a fictional Vietnamese bank could measure loanbook climate alignment (PACTA) and transition-risk stress (TRISK). Wave 0 (five commits, completed prior to this session) delivered a config-driven engagement runway: scripts/run_engagement.R can run the full delivery flow — intake through disclosure pack — for any bank, and tools/verify_refactor.R made the refactor acceptance bar ("does a change leave every CSV byte-identical?") a one-command check.

A same-day research pass (research/2026-07-25-post-wave0-platform-hardening-brainstorm.md) found that Wave 0's acceptance discipline had a precise blind spot: it verifies that run N+1 matches run N (reproducibility), but never that artifact A agrees with artifact B (consistency). Six defects live in exactly that blind spot — most visibly, the precomputed TRISK scenario grid powering the dashboard's Scenario Builder had gone stale three months earlier and now contradicts the base TRISK run on the same borrower under identical parameters.

Wave 1's objective is to close that blind spot structurally — build the detector, then use it to drive every fix — rather than patching the six defects ad hoc. This report covers the first two of six planned phases: building the detector (Phase 1) and using it to fix the three provenance/config-fidelity defects it found immediately (Phase 2).

04 / Assumptions & Constraints

Assumptions & Constraints

Binding Assumptions Applied

  • ASM-002 (evidence measured, not assumed): Holding four of the Scenario Builder's five levers fixed, the 243-cell grid contains only 27 distinct outcomes — risk_free_rate and carbon_price_family are currently inert. Deferred to Phase 4; not touched in Phases 1–2.
  • ASM-003 (batched refreeze): No golden literal is updated before Phase 6. Phases 2–5 are code commits verified by unit tests and invariants, not by byte-identity — the tree is expected to show real data drift (e.g. data_source column values) between now and the single Phase 6 refreeze.
  • ASM-004 (explicit opt-in): The public-snapshot guard rail moved from a bank_slug == "mcb-demo" string comparison to an explicit public_snapshot_allowed config key, defaulting FALSE.

Constraints Honored

  • CON-001: No new pipeline dependency introduced — the invariant checks use only packages already pinned in renv.lock (arrow, jsonlite, base R).
  • Repo law #5 (byte-identity): MCB's default 3-sector sector_priority_ranking.csv was regenerated and its md5 confirmed unchanged after the Phase 2 code edits.
  • A newly discovered constraint, fixed in-flight: jsonlite::toJSON() serializes a NULL list element as {}, which round-trips back as an empty named list, not NULL. The config validator was hardened to treat both shapes as "not configured" so a written-then-reread resolved config never breaks.
05 / Methodology

Methodology

The plan's own Decision Rule (DEC-001) required the detector to be built and proven to fail before any fix landed — mirroring the sequencing that worked in Wave 0, where the verification tool always preceded the refactor it would grade. Phase 1 was accepted only once tools/verify_refactor.R --invariants exited non-zero on the untouched tree, naming exactly the violations Phase 2 (and later phases) would fix. This turns "we believe the fix worked" into "the same command that found the defect now reports it gone."

Each of the five invariants was written as a pure, testable function taking a repo root (never the live tree implicitly) and returning a structured pass/fail result with human-readable detail. Every invariant is unit-tested against tempdir()-built fixtures — not the live repository — so the test suite stays green through every later phase regardless of what the live tree's data says at that moment. Only one invariant (INV-004, sector-list agreement) is additionally exercised against the live repo, because it is expected to already pass and exists purely to guard against future drift.

Phase 2 changes were verified at three levels: unit tests (testthat), a live subprocess run of the actual orchestrator (run_engagement.R executed end-to-end for SDB, not mocked), and a byte-for-byte diff of every changed CSV column to confirm the fix touched only the intended data_source column and nothing else.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the detector generalizes correctly. INV-004 and INV-005 passed on the very first run against the live tree, confirming the detector does not produce false positives on a healthy repository. This matters because a detector that cries wolf gets ignored; this one only flags what is actually wrong.

Finding 2 — provenance bugs are cheap to fix once found, expensive to find by hand. C2 (hardcoded data_source) was a one-line fix, but it had shipped silently in every non-MCB engagement's client-facing deliverable since the config-driven runway was built in Wave 0. Nothing in the byte-identity acceptance bar could have caught it, because MCB's own output never exercised the bug (its bank_slug happened to differ from the hardcoded literal only in casing/format, not in a way byte-identity checks against).

Finding 3 — fixing C4 surfaced a second, related defect not on the original list. Scoping prioritize_sectors() to cfg$trisk_sectors required tracing alignment_raw's min-max normalization, which was not scoped to configured sectors even though stress_raw and exposure_share_vec already were — an inconsistency within the same function. This is exactly the class of defect Wave 1 exists to find: not a crash, not a test failure, a value that's silently wrong only in configurations nobody had exercised yet.

Recommendation: proceed to Phase 3 next. It is a prerequisite for Phase 4 (per the plan's dependency graph — the ABCD regeneration must land before the grid is fingerprinted against final inputs) and has zero code dependency on anything Phase 2 touched, so it can start immediately.

08 / Implementation Path

Implementation Path

Phase 3 — Scenario Vintage & ABCD Single Source next

Retires the byte-identical duplicate scenario files (fixes INV-002) and adds the two missing provenance columns to the demo's ABCD data plus a validate_abcd_schema() gate. No dependency on Phase 2's changes beyond the detector itself.

Phase 4 — Grid Correctness

Fingerprints the scenario grid's inputs so a stale cache can never silently persist again (fixes INV-001 — the headline defect: the Scenario Builder currently disagrees with the TRISK Risk page for the same borrower). Also resolves whether the risk_free_rate lever is genuinely inert or a plumbing bug. Depends on Phase 3 completing first.

Phase 5 — Orchestrator Convergence

Makes scripts/run_engagement.R the single orchestrator; scripts/pipeline_refresh.R becomes a thin wrapper. Today the public MCB demo and every client engagement run through two different step lists — this is the highest-leverage remaining refactor, because it is what makes the Phase 6 CI guard cover MCB too.

Phase 6 — CI Guard, Refreeze, Docs

Adds the SDB CI job that Wave 0's final report claimed existed but does not (verified this session: no reference to run_engagement or sdb anywhere in .github/workflows/). Wires invariants into both CI workflows. Closes with the single golden refreeze the whole wave has been deferring (ASM-003).

09 / Risks / Open Questions

Risks / Open Questions

Open Risks Carried Into Phase 3+

  • RISK-001 (plan): the wave touches provenance, inputs, the grid, and the orchestrator before one refreeze — an unexplained numeric movement at Phase 6 would have several candidate causes. Mitigated by each phase's exit criteria isolating its own effect (already demonstrated in Phase 2: the diff touched only the data_source column).
  • RISK-002 (plan): the weekly refresh.yml auto-commit is not yet gated by invariants — a violated invariant does not block publishing until Phase 6 wires it in. Not a regression (it was never gated), but it means Phase 1's detector is currently informational-only in CI.
  • Phase 2 discovered a real jsonlite round-trip hazard (NULL → {} → empty list) that could recur anywhere a config is written and reread. Fixed for raw_loanbook_csv specifically; worth a grep for other optional config keys before Phase 5's orchestrator work adds more.

Questions Phase 3–4 Must Resolve

  • Is risk_free_rate's inertness a genuine trisk.model limitation or a parameter-plumbing bug in this repo? The plan's Specification S3 gives a measurement procedure and a binding default (remove the lever and bump the grid contract version) if it is confirmed inert — this has not yet been run.
  • Phase 4's grid regeneration is the wave's longest single operation (historically ~5 minutes per sector for 243 scenarios) — worth scheduling as its own session rather than folding into a mixed-task run.
  • Not yet answered: whether any other script beyond prioritize_sectors() silently ignores cfg$trisk_sectors. Not audited this session; a reasonable Phase 3 side-task.
