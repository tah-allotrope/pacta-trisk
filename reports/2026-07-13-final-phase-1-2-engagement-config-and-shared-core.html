Config-driven pipeline foundation for the PACTA + TRISK Vietnam platform: the first two phases of a six-phase plan to turn a single-bank demo into a repeatable client-engagement runway.

01 / Executive Summary

Executive Summary

What was done

Of the six-phase Client Engagement Runway plan, the first two phases are complete and committed to main. Phase 1 built a JSON engagement-configuration layer (R/engagement_config.R) and consolidated TRISK sector metadata that had been hand-duplicated across two — and, once verified, four — separate scripts into one registry (R/sector_registry.R). Phase 2 extracted the shared HTML-report and Vietnamese-name-matching helpers into reusable modules and parameterized the 1,385-line PACTA analysis script so its bank name, input files, and output directories all come from the engagement config instead of being hardcoded to "Mekong Commercial Bank."

Why it matters

The platform's pilot sales pack promises a bank "here is the file we need from you; we will return your alignment and transition-risk analysis" — but until now, the analysis code had never run against anything except the hand-built synthetic MCB CSVs. Every path and every "MCB" mention in the code was a literal string. This work is the prerequisite refactor that makes a second bank's engagement possible without duplicating the pipeline's ~3,100 lines of PACTA logic a second time.

02 / Background & Objective

Background & Objective

The pacta-trisk platform is a demo-complete PACTA (climate-alignment) and TRISK (transition-risk) analysis pipeline for a fictional Vietnamese bank, Mekong Commercial Bank (MCB), published as a public Streamlit dashboard. A prior hardening effort (completed 2026-07-10) proved the automated refresh pipeline, cut the published snapshot from ~108 MB to 3 MB, added a pinned R environment and a golden-number regression test suite, and ran a dress rehearsal of the intake layer against a deliberately dirty 40-row fixture loanbook for a second, fictional bank ("Saigon Delta Bank").

That rehearsal's own closing verdict named the one promise still undemonstrated: running the full PACTA and TRISK analysis — not just intake validation — on a loanbook other than MCB's. The root cause is that scripts/pacta_vietnam_scenario.R has no command-line arguments and hardcodes every input path, output directory, and instance of the bank's name. The Client Engagement Runway plan (plans/2026-07-13-client-engagement-runway-plan.md) lays out six phases to close that gap: an engagement-config layer, a shared R core, a TRISK-chain parameterization pass, a one-command orchestrator, a second-bank end-to-end run, and a set of data-dependency and methodology fixes. This report covers the first two.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding constraint honored throughout

With no --config flag, every script's observable output — file paths, CSV bytes, and the pipeline manifest shape — had to remain identical to the pre-refactor behavior, since the weekly auto-committing CI, the golden-number test suite, and the public dashboard all depend on it. Both phases were verified against this bar before committing (see Methodology).

Scope decisions made this session

  • Engagement configuration is JSON via jsonlite, not YAML — the YAML package is not pinned in renv.lock, and adding a new dependency for this was judged unnecessary.
  • The bank-name substitution reaches the full HTML report body, including the Vietnamese narrative prose — but the narrative's hardcoded factual figures (e.g. "2,000 tỷ VND cho vay xi măng") remain MCB-specific literals; rewriting the narrative to compute those figures from data is out of scope for this refactor and is a known limitation carried forward.
  • Two superseded PACTA scripts (pacta_demo.R, pacta_synthesis.R) were retired to attic/ rather than parameterized, after confirming via repo-wide search that nothing in scripts/, dashboard/, or CI referenced them.
05 / Methodology

Methodology

Each phase followed the same discipline: capture a pre-change baseline, make the code change, then prove the default (no-config) behavior is unaffected before committing.

  • Baseline capture: before any edit, the full R test suite and Python test suite were run to confirm a green starting point (89 R tests / 58 Python tests passing).
  • Byte-identity proof for Phase 1: the TRISK sector manifest (dashboard/data/trisk/manifest.csv) generated from the new shared registry was diffed against the pre-refactor version and found byte-for-byte identical; a full pipeline_refresh.R run reproduced the same 8-step "ok" manifest as before the change.
  • Byte-identity proof for Phase 2: all 7 synthesis_output/vietnam/*.csv outputs were MD5-hashed before and after parameterizing pacta_vietnam_scenario.R and found identical. The generated HTML report was diffed with embedded base64 PNG data stripped out (PNG re-encoding is not byte-stable across ggplot runs, a known, already-documented platform trait) — the remaining text content showed zero differences, confirming all ~30 "MCB" / "Mekong Commercial Bank" substitutions render identically under default config.
  • Full-chain regression: Rscript scripts/pipeline_refresh.R --full was run after each phase, exercising data generation, PACTA, the full TRISK chain, the 243-cell scenario grid, prioritization, and engagement scoring in sequence — reproducing the platform's known golden borrower ranking as an independent correctness signal.
  • Discovery during verification: running the full pipeline after Phase 1 surfaced two additional, previously un-grepped consumers of the old inline sector-metadata structure (trisk_scenario_grid.R and trisk_run_adhoc.R, the latter powering the dashboard's live-rerun feature) that the plan's file list had not anticipated. Both were fixed and verified in the same phase rather than deferred, since leaving them broken would have silently regressed the scenario grid and live-rerun features.
  • Scratch-data hygiene: full pipeline verification runs regenerate non-deterministic TRISK sensitivity-run folders (new UUIDs/timestamps every run) and re-render PNGs. These verification byproducts were reverted before each commit so the two phase commits contain only the intended code changes, not incidental data churn.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — Engagement Config Layer & Sector Registry Done

Introduced R/engagement_config.R: a JSON config loader whose built-in defaults reproduce today's MCB paths exactly, with validation that checks bank-name/slug well-formedness and confirms every input file exists before analysis begins. Introduced R/sector_registry.R, merging TRISK sector metadata (labels, units, alignment modes, scenario names, base run parameters) that had previously been maintained by hand in two separate places — a duplication that was one accidental edit away from silently drifting out of sync. Created engagements/mcb-demo/engagement_config.json as a documented example of the defaults.

Phase 2 — Shared R Core & PACTA Parameterization Done

Extracted the duplicated base64-image-encoding and HTML-writing helpers into R/report_toolkit.R, and the duplicated Vietnamese diacritic-normalization call into R/matching_helpers.R, wiring both into the four scripts that previously carried their own copies. Parameterized pacta_vietnam_scenario.R's input paths, output directories, and every occurrence of the bank's name — the single largest piece of this phase, since "MCB" text appeared far more densely (in Vietnamese narrative prose, chart titles, and the HTML report shell) than the plan's initial estimate suggested. Retired the two superseded demo scripts to attic/.

Phase 3 — TRISK Chain + Downstream Generators Not started

Planned next: give the remaining nine pipeline scripts (TRISK input prep, power/cement/steel demo runners, the scenario grid, prioritization, the dashboard snapshot copier, engagement scoring, and the letter/disclosure generators) the same --config support so an engagement can run its analysis entirely outside the MCB directory tree.

Phases 4–6 — Orchestrator, Second-Bank Run, Data Fixes Not started

Planned: a run_engagement.R one-command orchestrator; running the previously rehearsed "Saigon Delta Bank" fixture through the full analysis chain for the first time, with a second golden-number test set frozen from its output; and closing two external dependencies (a real asset-data sourcing decision, an asset-data intake contract) plus two known data-quality bugs.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the duplication was worse than documented. The plan's research inputs described TRISK sector metadata as duplicated in two places. Verification runs surfaced a third and fourth undocumented consumer of the same inline structure (the scenario-grid builder and the dashboard's live-rerun adapter). Both were silently broken by the Phase 1 refactor until caught by running the full pipeline rather than relying on the unit test suite alone — a signal that end-to-end verification, not just targeted tests, is doing real work in this codebase.

Finding 2 — the bank-name parameterization was a bigger surface than estimated. The plan's Phase 2 task description estimated "8 occurrences" of the bank name to replace; the actual count across chart titles, cat() banners, and the bilingual HTML report body was approximately 30. All were located and substituted, and the byte-identity proof (CSV hashes unchanged, HTML text-diff zero) gives confidence that none were missed or handled inconsistently.

Finding 3 — a known, carried-forward limitation. The Vietnamese narrative prose in the PACTA report contains hardcoded factual claims specific to MCB's actual loanbook (specific VND amounts, specific sector percentages) that are not computed from the input data. Swapping the bank's name in that prose was in scope and completed; making those specific claims data-driven for an arbitrary engagement was not, and remains true only for MCB today. This should be flagged explicitly if a future engagement's report is reviewed for accuracy.

Recommendation: proceed directly to Phase 3. The config-loading pattern and the verification discipline (baseline → change → byte-identity proof → full-pipeline regression) that worked for Phases 1–2 should be repeated for the nine remaining scripts, since Phase 3 is the direct prerequisite for the orchestrator (Phase 4) and the second-bank run (Phase 5) that demonstrate the platform's core commercial promise.

09 / Risks / Open Questions

Risks / Open Questions

Risks carried into Phase 3

  • The same "hidden consumer" risk that surfaced in Phase 1 (undocumented callers of shared logic) likely recurs across nine more scripts; each should be grepped for cross-references, not just edited in isolation.
  • Phase 5's second-bank run is expected to hit zero-match or empty-sector edge cases (the Saigon Delta Bank fixture was deliberately built with unmatchable rows) that Phases 1–2 have not exercised at all — those failure modes remain unverified until Phase 5 runs.

Open items

  • The Vietnamese narrative's hardcoded factual figures (noted in Finding 3) are an accepted, documented limitation rather than a resolved one — a future engagement's report should not be treated as fully data-driven without this caveat.
  • Phases 3–6 are unstarted; this report should not be read as evidence that the "one command, any bank" capability exists yet — only that its foundation is now in place and proven not to have regressed the existing MCB demo.
