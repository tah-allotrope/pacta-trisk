01 / Executive Summary

Executive Summary

What was done

The platform's TRISK analysis chain — previously three monolithic scripts hardcoded to the synthetic Mekong Commercial Bank (MCB) book — was decomposed into config-parameterized package functions (R/trisk_core.R, R/prioritization_core.R), mirroring the pattern already proven for PACTA. The four downstream generators (dashboard snapshot publisher, engagement scoring, engagement letters, disclosure pack) were then updated to read every path and the bank name from the same engagement config, so a non-MCB engagement can run end-to-end without writing into the public tree.

Why it matters

This closes the single largest gap between the platform's demo state and its commercial promise: running the whole PACTA + TRISK pipeline for a new bank's loanbook. Before this work, only the PACTA stage was config-driven — the TRISK chain and every client-facing output (scoring, letters, disclosure) still assumed MCB. Phases 1–2 make every pipeline stage parameterizable; only the orchestrator, a live rehearsal, and a handful of data-dependency closers remain.

02 / Background & Objective

Background & Objective

PACTA + TRISK Vietnam is a synthetic-data demonstration platform showing how a fictional Vietnamese bank ("Mekong Commercial Bank," MCB) could measure loanbook climate alignment (PACTA) and transition-risk stress (TRISK). A prior engineering-foundation effort decomposed the PACTA analysis into a genuinely loadable R package (pactatrisk) with an engagement-config layer, but — as the 2026-07-18 brainstorm (research/2026-07-18-runway-completion-and-credibility-brainstorm.md) documented — that foundation work landed before the "client-engagement runway" plan that was supposed to make the whole pipeline runnable for any bank. Only 2 of that runway's 6 phases had shipped: the TRISK chain, sector prioritization, snapshot publishing, engagement scoring, and the letter/disclosure generators all still hardcoded MCB's paths and bank name.

The objective of this plan (plans/2026-07-18-engagement-runway-completion-plan.md) is to finish that runway on top of the new package foundation, with one deliberate change from the original runway plan: merge the TRISK parameterization with a TRISK decompose into a single pass — since both operations touch the same ~1,300 lines of script, doing them separately would mean rewriting the same code twice under the same byte-identity acceptance gate. This report covers execution of Phases 1 and 2 of that plan.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding assumptions applied

  • ASM-002 (verbatim move): code was moved into functions with only path/bank-name parameterization — no logic edits. One accidental logic edit (dropping an undefined lib.loc = lib argument while moving TRISK-grid code) was caught and reverted to preserve the exact pre-existing behavior, including its latent (dormant, never actually executed) bug.
  • ASM-003 (volatility handling): a double-baseline run (two back-to-back executions of the unmodified pipeline) established that five TRISK output filenames per sector (npv_results_latest.csv, pd_results_latest.csv, params_latest.csv, company_trajectories_latest.csv, run_catalog.csv) carry a run_id/run_path UUID that trisk.model::run_trisk() regenerates on every invocation. These were excluded from the strict byte-identity comparison; every other CSV was held to byte-identity.
  • ASM-004 (side-copy scope): the legacy data/vietnam_trisk_*.csv duplicate files are now written only in default (MCB) mode, confirmed by grep that nothing else in the repo reads them.

Constraints & environment notes

  • R 4.5.2 via Rscript, not on PATH by default on this Windows machine (C:\Program Files\R\R-4.5.2\bin added to session PATH for every run).
  • core.autocrlf=true on this checkout made raw md5sum comparisons unreliable across git checkout operations; git diff (which normalizes line endings) was used as the authoritative byte-identity check instead, after confirming the discrepancy was a self-inflicted testing artifact.
  • The dashboard Python test environment initially lacked dashboard/requirements.txt dependencies; installed mid-session.
  • Confidence is high for Phases 1–2 (directly executed and verified this session). Confidence in Phase 3–5 scope/effort is inherited from the plan document and has not been re-validated by execution.
05 / Methodology

Methodology

Each phase followed the same discipline established by the prior PACTA decompose: capture a pre-change baseline, move code into functions with minimal, mechanical edits, run the full R test suite, run the full pipeline, and diff every output against the baseline before committing. For Phase 1, a genuine methodological gap was discovered mid-execution: a naive tools::md5sum() comparison across a git checkout ---reset tree produced 70 false-positive "drifted" files. Root-causing this (rather than accepting or silently re-baselining it) revealed it was core.autocrlf line-ending churn from the test harness itself, not a refactor defect — confirmed by re-checking with git diff --stat, which correctly normalizes line endings and showed the real diff was limited to intentional edits, PNG compression noise, timestamp text, and the known run_id volatility.

Both phases were verified with: the full testthat suite (Rscript -e "testthat::test_dir('tests/testthat')"), a full pipeline execution (Rscript scripts/pipeline_refresh.R and, for Phase 2, the --full variant which also regenerates PACTA and engagement scoring), a package load check (devtools::load_all('.')), and the Python dashboard suite (python -m pytest dashboard/tests). One Python test failure (test_auth.py::test_no_password_renders_landing, a hardcoded 3-second Streamlit AppTest timeout) was isolated by stashing all session changes and re-running against the untouched HEAD commit — it failed identically, confirming it as a pre-existing environmental flake rather than a regression.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — TRISK core decompose Done

Extracted scripts/trisk_prepare_inputs.R, scripts/trisk_sector_demo.R, and scripts/trisk_scenario_grid.R into R/trisk_core.R (trisk_prepare_sector_inputs(), trisk_run_sector(), trisk_run_grid() + supporting helpers), and scripts/sector_prioritization.R into R/prioritization_core.R (prioritize_sectors()). All four scripts became thin CLI wrappers that load an engagement config and call the core functions. scripts/trisk_run_adhoc.R was updated to source the new core file directly (the functions it depended on moved out of trisk_sector_demo.R). Added a backfill_zero_baseline() helper (unit-tested, not yet wired in — that's the Phase 5 Dung Quat fix) and a new tests/testthat/test_trisk_core.R with 13 test cases covering the grid, backfill, and path-resolution functions. Full suite after this phase: 162 passed, 0 failed.

Phase 2 — downstream generators Done

Config-drove scripts/refresh_dashboard_data.R (snapshot publisher), scripts/engagement_scoring.R, scripts/generate_engagement_letters.R, and scripts/generate_disclosure_pack.R. A real subprocess smoke test (tests/testthat/test_config_paths.R) caught a genuine bug: these scripts used file.path(getwd(), cfg$paths$X), which silently produces a broken concatenated path when a config supplies an absolute directory. Fixed by using cfg$paths$X directly, consistent with the repo law that every script already assumes it runs from the repo root.

Phase 3 — orchestrator Not started

Per the plan: extract R/step_runner.R from scripts/pipeline_refresh.R, add scripts/run_engagement.R with a --dry-run flag and a guard rail preventing a non-MCB config from writing into the public dashboard/data snapshot, and bump the package to v0.2.0.

Phase 4–5 — rehearsal & data closers Not started

Phase 4 runs the Saigon Delta Bank fixture end-to-end and freezes a second golden-number test set. Phase 5 writes the ABCD sourcing decision brief, versions the scenario inputs, and fixes the Dung Quat zero-baseline and power-2025 NA bugs. Both depend on Phase 3's orchestrator; Phase 5's ABCD brief has no code dependency and could start in parallel at any time.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the merge was the right call. Combining TRISK parameterization with the decompose in one pass, as the brainstorm recommended, meant the ~1,300 lines of TRISK script logic were touched exactly once under one byte-identity gate, instead of twice under two separate gates. This matches how the PACTA decompose was already proven safe in the prior foundation phase.

Finding 2 — the byte-identity discipline caught two real bugs before they shipped. The verbatim-move rule surfaced an accidental fix (the undefined lib variable) that would have silently changed behavior on a rare, previously impossible-to-trigger code path, and a subprocess smoke test caught a real absolute-path bug in every downstream generator that would only have surfaced once a real (non-relative-path) engagement config was used — i.e., during Phase 4's rehearsal, at a much more expensive point to debug.

Recommendation. Proceed directly to Phase 3. The plan's acceptance criteria for Phase 3 (step-runner extraction, --dry-run, the public-snapshot guard rail) are unblocked: every stage now accepts --config. Start Phase 5's ABCD sourcing brief in parallel — it has no code dependency and gates the commercial conversation for any real engagement.

09 / Risks / Open Questions

Risks / Open Questions

Risks carried forward

  • Phase 4 SDB fixture may hit deeper zero-match assumptions than inline guards can absorb (e.g., PACTA logic implicitly assuming every sector has matched exposure). The plan explicitly scopes Phase 4 to guard-and-log, not redesign — anything structural becomes a named backlog item.
  • The lib.loc = lib latent bug in the TRISK scenario-grid code (an undefined variable reference) was deliberately preserved rather than fixed, per the verbatim-move discipline. It has never executed in practice (the grid is always served from cache in the committed tree) but would crash a genuine full grid regeneration. This is now a known, documented risk rather than a silent one, and remains someone's call to fix in a future phase.
  • Python test environment for this sandbox required a mid-session dependency install; a CI environment following dashboard/requirements.txt exactly would not hit this.

Open questions for the next executor

  • Does Phase 3's run_engagement.R orchestrate via loaded pactatrisk:: functions in-process, or via system2("Rscript", ...) per step (matching pipeline_refresh.R's existing mechanism)? The plan's ALT-002 already resolves this in favor of script-chaining for process-isolation and failure-semantics reasons — worth re-confirming before implementation.
  • Should the accumulating synthesis_output/trisk/*_demo/runs/ archive (hundreds of timestamped directories, growing every pipeline run and every test run) be addressed before Phase 4 adds a second engagement's worth of runs? This is pre-existing repo behavior, not introduced by Phases 1–2, but it compounds with every future run.
