02 / Background & Objective

Background & Objective

PACTA + TRISK Vietnam is a synthetic-data demonstration platform showing how a fictional Vietnamese bank ("Mekong Commercial Bank") could measure loanbook climate alignment (PACTA) and transition-risk stress (TRISK), then turn the results into engagement and disclosure deliverables. An R pipeline produces the analysis; a frozen snapshot feeds a public Streamlit dashboard.

Two prior refactor phases (documented in commits d299496 and 408e95c) made the TRISK chain and every downstream generator config-parameterized, so any bank's engagement config — not just the built-in MCB defaults — can drive them. What remained missing was the thing that actually turns that capability into a demonstrated product: a single command that runs the whole flow end to end for a new bank, proof that it works on a second synthetic bank (not just MCB), and the last data-readiness gaps standing between a demo and a real client engagement.

This session's objective was to execute the first half of that closing work — the verification tooling that makes every future refactor's acceptance bar mechanical, and the orchestrator that makes "one command, any bank" real — while leaving the SDB rehearsal and data closers for the next session, rather than compress everything into one pass.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions applied

  • ASM-001: Verification tooling lives at tools/verify_refactor.R — dev-side only, no new pinned dependency, not sourced by any pipeline script.
  • DEC-004: The orchestrator chains steps as Rscript subprocesses via run_steps(), not in-process package calls — preserves today's per-step failure semantics and bounds memory across TRISK runs.
  • Deterministic TRISK run IDs (plan item N2 / ASM-003) are deliberately deferred to Phase 4, folded into that phase's single golden refreeze, rather than forcing an extra refreeze now.

Constraints in force

  • CON-001: No-flag (default MCB) behavior must remain byte-identical — verified after both phases via tools/verify_refactor.R.
  • CON-002: pipeline_manifest.json keys, step names, order, and counts are pinned by existing tests — the step-runner extraction could not change them.
  • CON-003: Streamlit Community Cloud has no R runtime — nothing in dashboard/ may gain an R dependency; run_engagement.R is operator-side only.
05 / Methodology

Methodology

Byte-identity verification. Every refactor in this codebase is held to the rule that default-mode CSV outputs must stay byte-identical. Two earlier phases proved this by hand-diffing; Phase 1 of this session codified that check into tools/verify_refactor.R, which runs the full pipeline refresh and classifies every changed tracked file (via git diff --name-only, chosen over raw md5sum because git normalizes Windows line-ending churn that a hash comparison would not) into PNG noise, expected timestamp/manifest churn, five named TRISK CSVs with known run_id/run_path volatility, or genuine drift. Anything in the last bucket fails the check.

Verbatim-move extraction. R/step_runner.R was extracted from scripts/pipeline_refresh.R by moving run_step/manifest logic without changing behavior — the same discipline the prior TRISK-core extraction used. This was proven, not assumed: after the extraction, a full pipeline run was diffed against the pre-extraction baseline and only the four intentionally-edited files (DESCRIPTION, NAMESPACE, README.md, scripts/pipeline_refresh.R) showed as changed.

Isolated proof runs. Because documentation edits (README additions) were made in the same working tree as the pipeline-output proof, each phase's acceptance run was performed with the doc edit temporarily set aside (git stash) so the tool's "untouched tree" claim was genuinely about pipeline output, not conflated with unrelated text changes.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — zero unexpected drift across both refactors. Two independent full-pipeline runs (one after Phase 1, one after Phase 2) each produced exactly the intended set of changed files and nothing else. This is direct evidence the verbatim-move discipline this codebase relies on continues to hold under a second application.

Finding 2 — a latent packaging gap, found and closed as a byproduct. Four TRISK-core functions (trisk_prepare_sector_inputs, trisk_run_sector, trisk_run_grid, prioritize_sectors) had carried @export roxygen tags since an earlier commit, but NAMESPACE had never been regenerated to include them — meaning the package's declared public API was silently narrower than its source intended. Regenerating NAMESPACE as part of Phase 2's package-version bump closed this gap alongside the two functions this phase actually added.

Finding 3 — test coverage grew with zero regressions. The R suite grew from 171 to 190 passing tests (+19, all new) across the two phases; the Python dashboard suite held steady at 58/58 throughout.

Recommendation. Proceed directly to Phase 3. Its two structural prerequisites — a mechanical byte-identity check and a working, tested orchestrator — are both now in place and independently verified, so the SDB rehearsal can begin without further groundwork.

09 / Risks / Open Questions

Risks / Open Questions

Known open risks

  • Five TRISK CSVs still carry non-deterministic run_id/run_path values between runs until Phase 4's fix lands — tools/verify_refactor.R currently treats this as expected, not resolved.
  • The "one command, any bank" flow has been unit- and dry-run-tested but not yet proven end-to-end against a second bank's real loanbook data (SDB fixture) — that is Phase 3's entire purpose.
  • Weekly CI does not yet guard against a "works only for MCB" regression; that guard is added in Phase 3.

Open questions carried into Phase 3

  • What structural guards the SDB run will actually need is unknown until it is run — the plan treats this as discovery, not something to pre-solve.
  • Whether the added weekly CI job's runtime fits comfortably alongside the existing refresh job (mitigated by running the SDB engagement with run_grid: false).
