01 / Executive Summary

Executive Summary

The defect

The synthetic Mekong Commercial Bank (MCB) loanbook that powers the public demo was denominated in millions of VND while its own loan_size_outstanding_currency column claimed "VND" outright — the generator's own source comment already said so ("All loan_size values in VND millions"), but the conversion was never applied. The portfolio totaled 25,020,000 raw units (≈ USD 950 at face value) instead of the ~USD 950 million the platform's own pitch deck and progress notes always claimed. Every borrower exposure, sector ranking, engagement letter, and disclosure figure computed from it was correct arithmetic on a scale that was wrong by exactly 1,000,000×.

What shipped

Two of a planned six phases are complete, tested, and pushed to main: a byte-identity CI gate that now runs on every push and blocks the weekly auto-publish job from ever committing a silent regression (Phase 1), and the units fix itself — the loanbook rescale, one shared money formatter replacing three ad-hoc copies, a new automated invariant (INV-006) that will catch this exact defect class if it recurs, and corrected documentation (Phase 2).

Verification, not assertion

Every claim in this report was independently re-verified this session, not carried forward from planning. The full pipeline was rerun end to end; the PACTA alignment outputs and TRISK dashboard snapshot were proven byte-identical before and after the rescale (confirming the fix touched only money columns, never ratios); all six cross-artifact invariants pass; and the second bank's engagement (Saigon Delta Bank) was rerun end to end to confirm the shared code paths — letters, disclosure packs, sector prioritization — are unaffected.

What's next

Four phases remain and none are started: replacing rank-relative priority scores with absolute anchored severity bands (Phase 3), a single golden refreeze consolidating that change (Phase 4), fixing the intake validator so it honors its own published schema instead of silently dropping real bank data (Phase 5), and a money-denominated coverage & reconciliation report per engagement (Phase 6). Phase 3 and Phase 5 have no unmet dependency and can start immediately.

02 / Background & Objective

Background & Objective

PACTA + TRISK Vietnam is a synthetic-data demonstration platform showing how a fictional Vietnamese bank ("Mekong Commercial Bank") could measure loanbook climate alignment (PACTA) and transition-risk stress (TRISK), feeding a public Streamlit dashboard and a full client-engagement delivery pipeline (intake, scoring, engagement letters, disclosure packs). Two prior hardening waves (Wave 0 "runway", Wave 1 "consistency") had already established a config-driven engagement orchestrator and a cross-artifact invariant checker that catches committed artifacts silently disagreeing with each other.

A fresh, from-scratch codebase review on 2026-07-27 — deliberately re-verifying every claim against the live repository rather than trusting prior session memory — found a defect class one layer removed from what Wave 1 checked: whether committed artifacts agree not just with each other, but with their own stated contracts (documentation, currency labels, CI claims). That review produced research/2026-07-27-post-wave1-contracts-units-and-guardrails-brainstorm.md, which was turned into a six-phase execution plan, plans/2026-07-27-contracts-units-and-guardrails-plan.md. This report covers the first two phases of that plan, executed and verified in this session.

04 / Assumptions & Constraints

Assumptions & Constraints

Assumptions applied

  • ASM-001 (loan literals are millions): the 43 call-site loan-size literals in the generator are correct at "millions of VND" scale; the defect was the missing ×1,000,000 conversion, not the literals themselves. Confirmed by the generator's own pre-existing source comment.
  • ASM-002 (rescale is ratio-neutral): multiplying every loan by the same constant should not change any PACTA alignment result, since PACTA market share and SDA intensity are ratio-based. This was tested, not assumed — see Findings.
  • DEC-001 (detector before fix): Phase 1 had to be green on the unmodified tree before any numeric change, so a later red result would be unambiguously caused by the change under test.

Constraints and one disclosed deviation

  • CON-001: every default-mode MCB CSV output must stay byte-identical to its pre-change content except where a phase explicitly refreezes it.
  • CON-002: no new package dependency — everything shipped uses base R plus packages already pinned in renv.lock.
  • Deviation from the plan's original batching intent, disclosed: the plan's DEC-002 called for Phase 2's and Phase 3's committed-artifact changes to land together in a single Phase 4 refreeze. Because this session executed only Phases 1–2, leaving Phase 2's code committed without refreezing the loanbook would have broken the very invariant (INV-006) Phase 2 introduces on the next CI run. Phase 2's commit therefore includes a money-only golden refreeze of the MCB artifacts, scoped strictly to money columns (verified — see Findings). Phase 4's refreeze, when it happens, now only needs to cover Phase 3's scoring changes.
05 / Methodology

Methodology

Both phases followed the same detector-first discipline the two prior hardening waves established: build and prove the automated check before making the change it exists to catch, so the fix's correctness rests on a machine-checkable gate rather than a read-through. Phase 1's byte-identity CI job was proven capable of failing — via a deliberate negative control that appended a byte to a tracked CSV, confirmed the classifier reported it as drift and exited non-zero, then restored the file — before Phase 2 touched a single number.

Every quantitative claim in this report was re-derived from a live command run in this session, not carried forward from the plan document. Ratio-invariance (the claim that PACTA's alignment outputs are untouched by the money rescale) was checked with git diff --name-only scoped to the exact ratio-bearing files, per the repo's own documented lesson that git status alone can produce false positives across CRLF-normalized files. The scenario grid's non-regeneration was confirmed by comparing its recorded input fingerprint (57600f19091de0077cb6a904d68e6c12) before and after the change, not merely by assuming it. A latent integer-overflow bug in the money formatters being replaced was caught by writing and running unit tests against trillion-scale figures before those formatters were wired into the pipeline, not discovered later in production output.

06 / Phase-by-Phase Analysis

Phase-by-Phase Analysis

Phase 1 — CI Guard Rails Done

Added a byte-identity job to .github/workflows/ci.yml that runs the pipeline's byte-identity acceptance check on every push and pull request — a check that existed as a local-only developer tool since Wave 0 but had never run in CI, despite CLAUDE.md claiming it did. Added a matching drift gate to the weekly refresh.yml auto-publish job, positioned immediately before the auto-commit step, with a workflow_dispatch escape hatch (allow_drift: true) for an intentional, reviewed refreeze. Corrected the two documents (CLAUDE.md, README.md) that had been describing CI behavior that didn't exist.

No analysis code changed in this phase — commit 994a1af, 6 files.

Phase 2 — Units Fix Done

Fixed the missing ×1,000,000 conversion at its single source (make_loan() in the data generator), consolidated three independent, ad-hoc VND formatters into one shared module (R/format_money.R), added INV-006 to the invariant checker to catch this defect class automatically going forward, and corrected five documents that had propagated the wrong scale into prose (three of them — the report README, the methodology doc, and the interpretation notes — had a second, independent 1,000× documentation error calling the exposure figure "billion" when even the flawed pre-fix data was "million"; this was fixed to "trillion" alongside the units fix).

A latent bug was found and fixed while building the shared formatter: the two formatters being replaced used formatC(x, format = "d"), which silently overflows via as.integer() coercion for any value past roughly 2.1 billion — exactly the range true-VND totals now reach. Caught by a unit test before it could have produced garbled figures in a real engagement letter. Commit cf2adeb, 47 files.

Phase 3 — Absolute Severity Scoring Not started

Would replace every min-max-normalized priority score (which makes the top-ranked sector or borrower always exactly 1.0, regardless of how bad it actually is) with severity computed against fixed, documented anchor tables. No dependency beyond Phase 1 — unblocked, can start immediately.

Phase 4 — Golden Refreeze Not started

Would regenerate every committed artifact affected by Phase 3's scoring change and re-pin the golden tests to values that are no longer tautologies. Depends on Phase 3; Phase 2's share of this work already landed (see the disclosed deviation in Assumptions & Constraints).

Phase 5 — Intake Contract Not started

Would make the loanbook intake validator honor its own published schema — it currently silently deletes rows using real-world ISIC power-sector codes and rejects USD-denominated exposure the schema explicitly says is accepted. No dependency beyond Phase 1 — unblocked, can run in parallel with Phases 2–4.

Phase 6 — Coverage & Reconciliation Report Not started

Would add a tracked, money-denominated report per engagement showing what a client submitted versus what the pipeline could process, and why. Depends on Phase 5.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the scale fix is exact and confirmed ratio-neutral. Before the fix, the MCB loanbook summed to 25,020,000 raw units under a currency column that said "VND" — a portfolio literally smaller than one loan's rounding error at true scale. After the fix, it sums to exactly 25,020,000,000,000 VND (≈ USD 950 million), landing in the same order of magnitude as the platform's second synthetic bank, Saigon Delta Bank, which was always denominated correctly. The chart below shows this on a logarithmic scale because the pre-fix and post-fix values differ by six orders of magnitude — a linear chart would render the "before" bar invisibly small.

Finding 2 — the fix did not leak into anything it shouldn't have. This was the primary risk of a rescale this large: PACTA's alignment and TRISK's stress-test outputs must depend only on the ratios between loan sizes, never their absolute value, or the rescale would silently distort every alignment gap and NPV figure in the platform. This was tested directly, not assumed: after a full pipeline rerun, every PACTA ratio-based output file (market-share alignment, SDA alignment, portfolio composition) and the entire TRISK dashboard snapshot came back byte-identical to their pre-fix content. Only files that legitimately contain a raw money column changed.

Finding 3 — an independent, older documentation error was found and fixed alongside it. Three prose documents described MCB's Decision-263 exposure as "19.3 billion VND" — but even under the old, flawed data this figure was 19.3 million, an unrelated 1,000× documentation slip that existed before this session and was masked by the larger units bug. Post-fix, the true figure is 19.3 trillion, and all three documents now say so.

Recommendation. Proceed to Phase 3 next. It is fully unblocked, and it closes the remaining gap this session's fixes did not touch: two golden-test assertions (composite_score[1] == 1.0) still hold today for any input, because Phase 2 deliberately left scoring logic untouched to keep this session's refreeze scoped to money columns only. Phase 5 (intake contract) is equally unblocked and could run in parallel by a second engineer, per the plan's own sequencing note.

09 / Risks / Open Questions

Risks / Open Questions

Disclosed risks

  • Two golden assertions remain tautological until Phase 3. test_golden_numbers.R and test_sdb_engagement.R both assert a top composite score of exactly 1.0, which is true today for any input under the still-unchanged min-max scoring. This is a known, disclosed gap that Phase 3 closes — it is not a regression introduced by this session's work.
  • man/ gained four new documentation pages as a side effect. Regenerating package documentation for the three new exported functions in R/format_money.R also surfaced four pre-existing, previously-undocumented internal functions in R/trisk_core.R that were never touched this session. Confirmed benign — no existing documentation file was modified, only new files added — but worth a human glance in code review.
  • Phase 2's refreeze narrows Phase 4's future scope. The plan's original design had Phases 2 and 3 sharing one combined refreeze commit in Phase 4. Because Phase 2 already committed its money-only refreeze (necessary to keep INV-006 passing in CI after this session — see Assumptions & Constraints), Phase 4 will now be a smaller, scoring-only refreeze. This is a disclosed, deliberate adaptation to the plan, not a silent deviation.

Open questions

  • None blocking. Phase 3 and Phase 5 are both immediately actionable per the dependency graph above.
  • The plan's Assumption ASM-002 (units fix does not conflict with the repo's "VND is never rescaled" law) was adopted as written in the plan; if a future reviewer reads that law differently, the plan's own RISK-004/ALT-001 entries document the fallback (correct the deck and progress notes downward instead of rescaling the generator).
