01 / Executive Summary

Executive Summary

What was done

All three phases in plans/2026-07-16-next-level-platform-foundation-plan.md were implemented, tested, and committed: (1) a new root CLAUDE.md documenting the repo's traps and conventions, with a refreshed AGENTS.md; (2) the decomposition of the PACTA analytics monolith (scripts/pacta_vietnam_scenario.R) into nine pure functions in a new R/pacta_core.R module, leaving the original script as a ~115-line orchestration wrapper; and (3) making pactatrisk a genuinely loadable R package — exported functions, a generated NAMESPACE, populated DESCRIPTION metadata, and a CI package-load check.

Why it matters

Before this work, the only way to verify a change to the PACTA pipeline was to run the entire 1,386-line script and diff CSVs by eye — slow, coarse, and unable to localize a regression to a specific stage. The platform also advertised an R package (pactatrisk 0.1.0 in DESCRIPTION) that could not actually be loaded. Both gaps are now closed: the analytics core is testable in seconds, and library(pactatrisk)-style consumption is real — the substrate the separate, larger client-engagement-runway effort will build on when running the pipeline for additional banks.

Verification

Every synthesis_output/vietnam/*.csv file was confirmed byte-identical (MD5) to the pre-refactor baseline after both the PHASE-02 decompose and the PHASE-03 package changes. devtools::test() passed 130/130, and devtools::build() produced a clean 35 KB tarball with zero warnings.

An unplanned discovery, fixed at the root

Implementing Phase 3 surfaced a real architectural collision the plan hadn't anticipated: R treats a top-level data/ directory as reserved package-data space, and package-loading tools were executing this repo's data/generate_vietnam_data.R as a side effect, crashing the load. Fixed by relocating that one script to scripts/ (where every other pipeline stage script already lives) — see Findings below for the full reasoning.

02 / Background & Objective

Background & Objective

PACTA + TRISK Vietnam is a synthetic-data demonstration platform showing how a fictional Vietnamese bank ("Mekong Commercial Bank", MCB) could measure loanbook climate alignment (PACTA) and transition-risk stress (TRISK). A prior brainstorm (research/2026-07-16-next-level-platform-brainstorm.md) surveyed the whole codebase for what would take the platform to the next level and identified two layers of work: finishing an already-planned "client engagement runway" (parameterizing the full pipeline for any bank, not just MCB), and, underneath that, an engineering-foundation gap the runway plan had not fully closed — the PACTA analytics core remained an untestable monolith, and the repo's advertised R package did not actually function as one.

The objective of the resulting plan was narrow and mechanical by design: extract the PACTA script's nine logical sections into pure, individually testable functions without changing any analysis logic, and write down the repo's sharp, easy-to-rediscover-the-hard-way rules (VND is never rescaled, run everything from the repo root, the golden-number tests are load-bearing, and so on) so future refactors — by a human or an agent — start from a documented baseline instead of an archaeology dig.

04 / Assumptions & Constraints

Assumptions & Constraints

Binding assumptions applied

  • ASM-001/002: a single new file, R/pacta_core.R; code moved verbatim into function bodies with only mechanical renames (e.g. vn_output → output_dir) — no logic edits, no dplyr pipeline "tidy-ups".
  • ASM-003: chart and HTML-report code extracted for symmetry but verified visually/structurally, not by hash (PNG compression and HTML timestamps are inherently nondeterministic).
  • ASM-004: network install of roxygen2/devtools was available, so the primary path (install + add to renv.lock) was used rather than the hand-written-NAMESPACE fallback.
  • ASM-006: only @export roxygen tags were added, never @import/@importFrom, so the existing source()-based scripts keep working unchanged — verified directly.

Constraints honored

  • CON-001: every synthesis_output/vietnam/*.csv file byte-identical pre- vs post-refactor — verified via MD5 after every phase.
  • CON-002: the only new dependencies added across all three phases are the dev-only roxygen2/devtools pair for PHASE-03, added via a targeted renv::record() call (not a full renv::snapshot()) and diffed to confirm no existing pipeline package was pruned.
05 / Methodology

Methodology

Each phase followed the same sequence: implement the file changes specified in the plan, run the full R test suite (testthat::test_dir('tests/testthat')), fix any failure before proceeding, stage, and commit with a descriptive message — never committing on a red suite.

For the PACTA decompose specifically, the safety net was a pre-refactor baseline: the original monolith was run once to produce synthesis_output/vietnam/*.csv, and an MD5 checksum was recorded for every CSV. After the decompose, the script was re-run and every checksum re-compared. This turns "did the refactor change anything observable" into a mechanical yes/no check rather than a manual read-through of a 1,386-line diff.

07 / Findings & Recommendation

Findings & Recommendation

Finding 1 — the decompose was byte-identical on the first attempt. All 7 published CSVs matched their pre-refactor MD5 hashes with no iteration needed, which is a direct result of the plan's "move code verbatim, only promote read-variables to parameters" discipline rather than a lucky outcome to be repeated casually on future refactors.

Finding 2 — the original monolith's section boundaries were already well-formed function boundaries. Each of the nine # SECTION banners in the old script corresponded cleanly to one function with a small, well-defined set of inputs and outputs; the only real cross-section coupling was two derived variables (abcd_norm, the PDP8 target-metric names) that needed to flow through return values, both handled explicitly in the new module's signatures.

Finding 3 — the module's line count grew, and that's expected. R/pacta_core.R is 1,422 lines versus the original script's 1,386, because each function now carries a short roxygen-style doc comment. The maintainability win is not fewer lines; it's that the wrapper script is now 115 lines and any one analysis stage can be tested or modified in isolation.

Finding 4 — the plan under-anticipated one real technical obstacle. Making the package loadable required more than tagging functions and writing NAMESPACE: pkgload::load_all() (used by devtools::load_all(), devtools::test(), and roxygen2::roxygenise()'s default strategy) treats a top-level data/ directory as reserved R-package data space and executes every *.R file inside it as a "lazy data" script. This repo's data/generate_vietnam_data.R collided with that convention and crashed package loading outright — not a warning, a hard halt. The root-cause fix was to relocate that one script to scripts/ (updating 3 references: scripts/pipeline_refresh.R's step path, a header comment, and an error-message string), which is also a consistency improvement independent of the bug — it was the only pipeline stage script not already living in scripts/. Verified the relocated script still produces byte-identical output CSVs from its new location.

Finding 5 — .Rbuildignore has no comment syntax. A first attempt at .Rbuildignore included a #-prefixed explanatory comment line, following .gitignore convention. R treats every non-blank line as a literal Perl regex with no comment support, so the build failed with an "invalid regular expression" error. Fixed by keeping the file pure pattern-per-line, matching every existing entry's style.

Recommendation: this plan is now fully executed. The natural next units of work are (a) the separate client-engagement-runway plan's remaining phases, which can now build on a loadable, testable pactatrisk core, and (b) applying the same decompose-into-functions pattern to the TRISK scripts once a second real engagement makes that refactor's payoff concrete. Neither should be bundled with this foundation work retroactively — keep them as separate, reviewable efforts.

09 / Risks / Open Questions

Risks / Open Questions

Resolved: the data/ collision is fixed, not papered over

The data/-directory collision (Finding 4) is fixed at its root cause — the offending script moved out of reserved package-data space — rather than worked around with a fragile ignore hack. This was verified by re-running devtools::load_all('.'), devtools::test(), and the relocated generator script itself (byte-identical CSV output) after the move.

Open: R CMD check was not run

devtools::build() succeeded cleanly, and devtools::test() passed — both explicit exit criteria. The stricter R CMD check (which would exercise tests/testthat.R's library(pactatrisk) call against a freshly-installed copy) was not run in this session, since Rtools is not installed in this Windows environment (a build-tools warning appeared but did not block the tarball build, which has no compiled code to build). Worth running once Rtools is available, though it is not a named exit criterion of this plan.

Non-risk: PNG/HTML nondeterminism

Regenerated PNGs and HTML reports changed in git diffs during verification. This is expected and explicitly allowed by the plan's acceptance bar (PNG compression is nondeterministic; HTML reports differ only in the generated-timestamp text). No CSV drift occurred at any point across all three phases.

Caught in verification: an over-broad regression check

Confirming the relocated data/generate_vietnam_data.R didn't break the pipeline involved running Rscript scripts/pipeline_refresh.R in full, which legitimately regenerated the public dashboard/data/ snapshot and TRISK sensitivity run artifacts — output unrelated to this plan's scope. Those regenerated files were identified and reverted via git checkout -- before committing, so PHASE-03's commit contains only its intended changes. (One recovery step in that process briefly over-deleted a pre-existing tracked run-history directory via an overly broad rm -rf; it was restored immediately via git checkout -- before anything was staged. No data loss occurred, but a narrower revert command would have avoided the extra step.)

Open: Python test suite not re-verified

dashboard/tests was not run in this session because pytest was not installed in the execution environment, and this plan's scope never touches dashboard/ code. Low risk, but worth confirming in CI (where python-tests already runs on every push).
